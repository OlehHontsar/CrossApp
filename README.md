# CrossApp 
Наскрізний проєкт з крос-платформного програмування. 
Предметна область: Замовлення. Сутності: Customer, Product, Order, OrderLine. 
Призначення: оформлення замовлень і підрахунок сум. 

## Керування проєктом та CLI команди розробника
```bash
# Збірка всього рішення
dotnet build 

# Локальний запуск застосунку (Зчитування імпорту та демонстрація бізнес-правил домену)
dotnet run --project src/Cli 

# Локальний запуск застосунку з явним вказанням JSON-файлу
dotnet run --project src/Cli data/sample.json
```

## Середовище Розробки 
.NET SDK 10.0, Windows 11 x64

## Лабораторна робота 2 & 3: Модульність рішення, Multi-targeting та Відмовостійкий Імпорт

### Специфікація архітектурного розділення (SoC)
Уся системна та бізнес-логіка повністю інкапсульована в крос-платформній бібліотеці класів (`Core`). Консольний застосунок (`Cli`) виконує роль виключно представлення даних (UI). 
Згідно з архітектурною конвенцією на семестр, у проєкті `Core` розгорнуто таку структуру каталогів для нашої предметної області:
* `Core/Dto/` — record-типи формату даних (тиждень 3): `ProductDto`, `WarehouseDto`, `ImportResult`
* `Core/Domain/` — сутності з поведінкою та інваріантами (тиждень 4) [Реалізовано]
* `Core/Storage/` — реалізації сховищ даних (тиждень 5) [Заглушка .gitkeep]
* `Core/Import/` — логіка відмовостійких імпортерів (CSV / JSON)

## Лабораторна робота 4: Доменна модель, інваріанти та інкапсуляція

В межах роботи анемічну модель даних розділено на чисті формати обміну (**DTO**) та повноцінні об'єкти бізнес-поведінки (**Сутності**). Стан моделі повністю інкапсульовано у приватному полі, а пряма модифікація властивостей ззовні заблокована відсутністю публічних сетерів. Нові екземпляри сутності створюються виключно через статичний фабричний метод `Create()`.

### Специфікація захищених бізнес-інваріантів домену
1. **Валідація текстових ключів:** Критичні текстові ідентифікатори об'єкта (`Id`, `Sku`, `Name`) не можуть бути порожніми або складатися виключно з пробілів. Порушення правила викликає `ArgumentException`.
2. **Невід'ємність стартового балансу:** Початкова кількість одиниць товару при ініціалізації картки в системі не може бути меншою за нуль. Спроба передати від'ємне значення викликає `ArgumentOutOfRangeException`.
3. **Обмеження на обсяг операцій:** Кількість товару в методах приходу `RegisterArrival` та списання `Issue` обов'язково має бути строго додатним числом (> 0), інакше генерується `ArgumentOutOfRangeException`.
4. **Захист від дефіциту залишків:** Кількість наявного матеріалу на складі ніколи не може стати меншою за нуль. Якщо бізнес-операція `Issue` вимагає списати більше одиниць, ніж є на балансі об'єкта, процес блокується та викидає `InvalidOperationException`.

## Лабораторна робота 5: Сервісний шар, інтерфейси, два сховища та ручний DI

У цій роботі забезпечено повну незалежність доменної логіки від способу зберігання даних завдяки виділенню абстракції сховища (`ICatalogStore`). 

### Архітектурні компоненти
1. **Контракт (`ICatalogStore`):** Визначає єдиний доменний інтерфейс для операцій `List`, `GetById`, `Add`, `Update`, та `Remove`.
2. **Сховище в пам'яті (`InMemoryCatalogStore`):** Зберігає дані у словнику `Dictionary` під час сеансу роботи (з ініціалізацією через `SampleData`).
3. **Файлове сховище (`FileCatalogStore`):** Забезпечує кешування в пам'яті та автоматичну серіалізацію/десеріалізацію стану в JSON-файл (`catalog.json`) через мапінг у DTO.
4. **Сервісний шар (`CatalogService`):** Інкапсулює бізнес-сценарії (додавання, прихід товару тощо) та приймає сховище через конструктор (Dependency Inversion).
5. **Composition Root (`Program.cs`):** Єдина точка вжитку, де виконується ручне впровадження залежностей (Manual DI) та вибір режиму роботи залежно від аргументу командного рядка (`--file`).

## Лабораторна робота 6: Доменні події, делегати Action/Func, лямбди

У цій роботі реалізовано механізм сповіщення зовнішніх компонентів про зміни стану без порушення принципу ізоляції доменного шару (патерн **Observer**).

### Архітектурні особливості та реалізація
1. **Інфраструктура подій у `Core`:**
   - `CatalogChangeKind` (enum): класифікація типів подій (`Added`, `Received`, `Issued`, `Removed`).
   - `CatalogChangedEventArgs`: клас даних події (нащадок `EventArgs`), що містить ID товару, тип зміни, дельту, залишок після операції та мітку часу (`DateTimeOffset.At`).
2. **Безпечне підняття подій у `CatalogService`:**
   - Подія `event EventHandler<CatalogChangedEventArgs>? Changed` викликається виключно після успішного проходження доменних інваріантів і зміни стану (`?.Invoke`). Якщо операція падає на валідації, подія не генерується.
   - Використання делегата `Func<Product, bool>` у методі `FindAll()` для гнучкої фільтрації даних (коли потрібен результат, а не просто сповіщення).
3. **Обробка та логування в `Cli` (`Program.cs`):**
   - **Перший підписник:** локальний метод `OnCatalogChanged`, який форматує повідомлення та паралельно виводить його в консоль і дописує у файл `logs/app.log` (каталог створюється динамічно через `Directory.CreateDirectory`).
   - **Другий підписник:** лямбда-вираз із замиканням над зовнішньою змінною-лічильником (`changes`), що демонструє синхронне виконання обробників у порядку підписки.
   - **Тестування відписки (`-=`) та інваріантів:** продемонстровано припинення логування після відписки конкретного обробника, а також відсутність генерації подій при відмовах бізнес-логіки.

   ## Лабораторна робота № 7: Звіти через LINQ (LINQ to Objects)

### 1. Реалізовані DTO та сервіси
- **DTOs (`src/Core/Reports/`)**:
  - `StockLine` (`record`): представлення товару у звітах (`Sku`, `Name`, `Quantity`, `Unit`).
  - `GroupSummary` (`record`): результати групування (`Key`, `Count`, `TotalQuantity`).
- **`ReportService` (`src/Core/Reports/ReportService.cs`)**:
  - `TopByQuantity(source, n)` — Топ-N товарів за залишком зі стабільним другим ключем сортування (`ThenBy`).
  - `LowStock(source, threshold)` — фільтрація товарів, дефіцит яких менший за поріг.
  - `ByUnit(source)` — групування товарів за одиницею виміру (`GroupBy`) з підрахунком суми та кількості.
  - `Totals(source)` — агрегатні обчислення (`Count`, `Sum`, `Average`, `Max`) з безпечною обробкою порожніх колекцій.

### Лабораторна робота № 9: Конфігурація додатків, ієрархія джерел та User Secrets
- **Ієрархія джерел конфігурації**: `appsettings.json` (дефолти) $\rightarrow$ `appsettings.{Environment}.json` $\rightarrow$ `user-secrets` $\rightarrow$ Змінні середовища (`CROSSAPP_*`) $\rightarrow$ Аргументи командного рядка (найвищий пріоритет)[cite: 2].
- **Ізоляція секретів (`dotnet user-secrets`)**: Чутливі дані (`Integration:ApiKey`) винесені у захищене системне сховище ОС, а сам файл `appsettings.json` у репозиторії залишається чистим від секретів[cite: 2, 5, 6].
- **Шляхо-незалежність**: Використання `AppContext.BaseDirectory` для стабільного пошуку файлів незалежно від поточної робочої директорії термінала[cite: 1, 2].
