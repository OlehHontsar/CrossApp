# CrossApp 
Наскрізний проєкт з крос-платформного програмування. 
Предметна область: Замовлення. Сутності: Customer, Product, Order, OrderLine. 
Призначення: оформлення замовлень і підрахунок сум. 

## Керування проєктом та CLI команди розробника
```bash
# Збірка всього рішення
dotnet build 

# Локальний запуск застосунку (Зчитування імпорту та демонстрація бізнес-правил домену)
dotnet run --project src/Cli 

# Локальний запуск застосунку з явним вказанням JSON-файлу
dotnet run --project src/Cli data/sample.json
```

## Середовище Розробки 
.NET SDK 10.0, Windows 11 x64

## Лабораторна робота 2 & 3: Модульність рішення, Multi-targeting та Відмовостійкий Імпорт

### Специфікація архітектурного розділення (SoC)
Уся системна та бізнес-логіка повністю інкапсульована в крос-платформній бібліотеці класів (`Core`). Консольний застосунок (`Cli`) виконує роль виключно представлення даних (UI). 
Згідно з архітектурною конвенцією на семестр, у проєкті `Core` розгорнуто таку структуру каталогів для нашої предметної області:
* `Core/Dto/` — record-типи формату даних (тиждень 3): `ProductDto`, `WarehouseDto`, `ImportResult`
* `Core/Domain/` — сутності з поведінкою та інваріантами (тиждень 4) [Реалізовано]
* `Core/Storage/` — реалізації сховищ даних (тиждень 5) [Заглушка .gitkeep]
* `Core/Import/` — логіка відмовостійких імпортерів (CSV / JSON)

### Поточна структура каталогів рішення
```text

├── CrossApp.slnx            # Сучасний файл рішення XML-формату

    │   ├── EnvironmentInfo.cs
    │   ├── Dto/             # Розділені транспортні рекорди даних
    │   │   ├── ImportResult.cs
    │   │   └── ProductDto.cs
    │   ├── Domain/          # Чиста бізнес-поведінка та захист доменного стану
    │   │   └── Product.cs

        └── Program.cs       # Сценарії «успіх» + «порушення інваріанту» (Лаб 4)
```

### Результати порівняння конфігурацій публікації (Лаб 2)

Збірка та заміри розмірів вихідних папок здійснювалися на ОС **Windows 11 x64** за допомогою команд:
* `dotnet publish src/Cli -c Release -r win-x64 --self-contained true`
* `dotnet publish src/Cli -c Release -r win-x64 --self-contained true -p:PublishTrimmed=true`
* `dotnet publish src/Cli -c Release -r win-x64 --self-contained false`

| RID | Режим публікації / Параметри | Розмір publish | Потрібен runtime | Особливості розгортання файлів |
| :--- | :--- | :--- | :--- | :--- |
| **win-x64** | `self-contained true` | **76.68 МБ** | ні | Повна автономність, ~200+ системних `.dll` файлів у комплекті. |
| **win-x64** | `self-contained` + `PublishTrimmed=true` | **12.35 МБ** | ні | Максимальна оптимізація. Статичний лінкер вирізав ~64 МБ мертвого коду .NET. |
| **win-x64** | `framework-dependent` (`false`) | **0.19 МБ** | так (.NET 10) | Мінімальний розмір, але вимагає попередньо встановленого SDK у клієнта. |

### Результати тестування відмовостійкого імпорту (Лаб 3)
Для перевірки стійкості додатка у файл `data/sample.csv` було внесено 3 дефектні рядки. Застосунок успішно локалізував помилки та вивів їх у термінал, не перериваючи імпорт решти 10 цілісних записів:
* **Рядок 12:** Менше 5 колонок даних (відпрацював патерн властивості `{ Length: < 5 }`).
* **Рядок 13:** Текстове значення кількості `"багато"` (відпрацював патерн списку з фільтром `when !int.TryParse`).
* **Рядок 14:** Порожнє обов'язкове поле артикулу (відпрацював комбінований логічний патерн `or`).

## Лабораторна робота 4: Доменна модель, інваріанти та інкапсуляція

В межах роботи анемічну модель даних розділено на чисті формати обміну (**DTO**) та повноцінні об'єкти бізнес-поведінки (**Сутності**). Стан моделі повністю інкапсульовано у приватному полі, а пряма модифікація властивостей ззовні заблокована відсутністю публічних сетерів. Нові екземпляри сутності створюються виключно через статичний фабричний метод `Create()`.

### Специфікація захищених бізнес-інваріантів домену
1. **Валідація текстових ключів:** Критичні текстові ідентифікатори об'єкта (`Id`, `Sku`, `Name`) не можуть бути порожніми або складатися виключно з пробілів. Порушення правила викликає `ArgumentException`.
2. **Невід'ємність стартового балансу:** Початкова кількість одиниць товару при ініціалізації картки в системі не може бути меншою за нуль. Спроба передати від'ємне значення викликає `ArgumentOutOfRangeException`.
3. **Обмеження на обсяг операцій:** Кількість товару в методах приходу `RegisterArrival` та списання `Issue` обов'язково має бути строго додатним числом (> 0), інакше генерується `ArgumentOutOfRangeException`.
4. **Захист від дефіциту залишків:** Кількість наявного матеріалу на складі ніколи не може стати меншою за нуль. Якщо бізнес-операція `Issue` вимагає списати більше одиниць, ніж є на балансі об'єкта, процес блокується та викидає `InvalidOperationException`.
